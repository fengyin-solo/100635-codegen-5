# 投运前验收与移交台账 · 规则裁决书

> 适用范围：城市地下综合管廊新管廊投运前的验收、移交、缺陷责任期管理。
> 生效方式：本文件中的裁决规则直接固化在 `frontend/src/api/handover-service.ts`，页面不做业务判断，
> 任何入口（页面、回填、同步）都只能调用同一套规则引擎。

## 0. 要解决的问题

1. 验收在建设单位手里、移交清单在接收单位手里，两套皮、对不上账。
2. 接收单位的人能替建设单位改验收结论；谁批的、什么时间批的查无实据。
3. 缺陷责任期内遗留问题无人盯，到期不了了之。
4. 同一张移交单反复提交产生重复数据；两个单位对同一缺陷判定打架。
5. 存量移交单、早年无书面交接、往期巡检数据没有统一回填口径。
6. 同步断线后乱序、拿上一条值顶替；概览和看板条数两个数。

---

## 1. 认单位：归属模型（核心）

### 1.1 每张移交单强制登记

- 移交单编号（全局唯一自然键）
- **验收单位**（验收结论的归属单位，即组织验收的建设单位）、验收人
- 接收单位
- 验收日期、移交日期
- 缺陷责任期截止日
- 验收结论（合格 / 有条件合格 / 不合格 / 待补验（补建））
- 数据来源（正式移交 / 补建-事实移交 / 往期回填）

归属信息随记录持久化，不依赖当前登录人推断。

### 1.2 字段级归属矩阵

| 数据 | 归属 | 非归属方 |
| --- | --- | --- |
| 移交单元数据（编号、管廊、日期、责任期） | 验收单位建档，提交后锁定 | 只读 |
| **验收结论、验收人签字、验收审批** | **仅验收单位的验收人**（单位 + 角色双匹配） | 只读 |
| 接收确认 | 仅接收单位 | 只读 |
| 建设单位缺陷判定 | 建设单位 | 只读 |
| 接收单位缺陷判定 | 接收单位 | 只读 |
| 受控待办闭环 | 仅待办的责任单位 | 只读 |

- 监理单位、管线单位等第三方对全单只读。
- 审批人、审批单位、审批时间由系统按当前会话身份与系统时钟生成，**不可由表单手填、不可篡改**；
  验收结论每次变更追加一条不可改的版本记录。"谁批的、什么时候批的"以此为准。

### 1.3 越权写入的处置

越权修改一律**在写入前拦截**：业务数据零改动，返回 `驳回：归属冲突`，并写明
"该字段归属××单位，××单位仅可读"。驳回事件进入审计台账（操作人、单位、目标单、字段、时间、冲突说明），
审计记录不是业务数据，仅供追溯。

> 直接修复的乱象：接收单位的人替建设单位改验收结论——该路径在服务层不存在。

## 2. 验收结论与异常结论

### 2.1 结论流转

`待验收 → 已验收（验收单位验收人审批）→ 已移交（接收单位确认）`。
补建单允许处于 `补建待确认`，确认前结论位只能是 `待补验（补建）`，**禁止补造"合格"**。

### 2.2 异常结论 → 待查台账（唯一待查入口）

命中以下任一情形，系统自动把异常结论写入**全局唯一的待查台账**：

1. 结论为"合格/有条件合格"，但存在未闭环的严重或危急缺陷；
2. 验收日期缺失，或晚于移交日期/实际投运日期；
3. 已移交但无验收结论或无验收人签字；
4. 同一移交单编号重复提交且内容不一致；
5. 补建单已过默认缺陷责任期且仍有遗留问题（见 §5.3）；
6. 同步进来的事件缺关键字段或载荷为空（见 §7）。

所有入口（移交台账、巡检入口、回填、同步）发现异常，只写这一本待查台账；
概览卡片、看板、各入口读到的待查条数来自同一个读数函数，不允许各算各的。
待查项处置结果只能是"已核实"或"已排除"，不允许直接删除。

## 3. 缺陷责任期：受控待办 → 到期自动转隐患

### 3.1 受控待办

- 验收发现的每一处遗留问题，在锁定判定后**立即生成一条受控待办**：
  内容、来源移交单、来源缺陷、责任单位、责任人、要求闭环日期（= 缺陷责任期截止日与整改要求日取较早者）。
- 待办只有 `待整改 / 整改中 / 已闭环 / 已转隐患` 四个状态；闭环必须由责任单位操作并记录闭环时间。
- 待办与移交单、缺陷双向挂编号，可追溯。

### 3.2 到期自动转隐患

- 系统每日（演示环境按"模拟日期"按钮触发跑批）扫描：**要求闭环日期 < 当前日期且未闭环**的待办，
  自动生成一条隐患记录写入隐患整改模块，整改状态 = `待整改`——隐患整改那边因此多出一条待整改。
  原待办置 `已转隐患`，缺陷置 `已转隐患`，全程留痕。
- 转换幂等：以"来源待办编号"为幂等键，重复跑批不产生第二条隐患。

## 4. 判定打架与规则冲突：一律取严

### 4.1 两个单位对同一处缺陷判定打架（裁决）

**裁决：以更严的一档判定为准；两档同级别时，以接收单位（运维方）判定为准。**

依据：

1. **就严不就宽（本台账总原则，见 §4.3）**：缺陷整改的成本在建设阶段，漏判的代价是运行期安全事故，
   取舍必须偏向风险承受方；
2. **谁运行、谁负责**：管廊投运后的运行安全主体责任在接收单位，其现场复核对运行风险负责，
   同档分歧由其落锤；
3. 验收结论字段的归属不变——接收单位仍然**不能改验收结论**（§1.2）；
   打架的处理结果落在"缺陷判定/受控待办"这一独立链路上，两条链路互不越界；
4. 宽松的一档不删除、不覆盖，**降级为提示**挂在缺陷记录上（谁判的、判的什么、何时判的均保留）。

严重度排序：`一般 < 严重 < 危急`。任一单位判定"需整改"即按需整改受控。
首次判定即对该档生效受控（不等对方表态，避免僵持期间失控）；第二次判定到达后按上述规则重新仲裁。

### 4.2 重复提交：按移交单编号去重

- 同一移交单编号 + 同一内容再次提交：幂等返回原单，不新增单据、不新增操作日志。
- 同一编号 + 内容不一致：**驳回本次写入**，原单不动，冲突写入待查台账（§2.2 第 4 项），人工裁决。

### 4.3 规则冲突的通用取舍

任何两条规则对同一事项给出不同宽严要求时：

- 从严档**强制执行**；
- 从宽档**降级为提示**，作为备注保留，不阻断业务但不再作为放行依据。

典型场景：缺陷责任期合同约定 12 个月、但法定/设计文件要求 24 个月 → 按 24 个月强制执行，
12 个月仅留作提示。

## 5. 存量数据回填与早年补建（裁决）

### 5.1 回填顺序（两阶段，保证自洽）

1. **阶段 A：移交单骨架，按验收日期升序回填**（同日按移交单编号升序）。
   每条走与新单相同的写入引擎：绑定验收单位、校验归属、去重、异常结论进待查。
   关键字段缺失的**不建单**，转入缺项清单。
2. **阶段 B：往期明细，按巡检日期升序整体搬入**，挂接到已有效的移交单：
   - 归属单不存在或仍在缺项待确认：明细不得自动挂靠，转缺项清单等待人工确认；
   - 巡检日期早于归属单验收日期：时序矛盾，转待查台账。

先立骨架、后挂明细、按日期升序，保证任何时刻挂接关系都成立、责任期计算不悬空。

### 5.2 缺失项处理

- 缺失项逐条生成缺项清单（来源批次、原始摘要、缺失字段），状态 `待确认`。
- **确认前不计入有效条数、不参与到期转隐患、不进概览有效口径**，只单独计"待确认"数；
  杜绝假数据驱动真隐患。
- 人工逐条确认（补齐字段或选定归属单）后，按当前规则引擎**即时重放**（绑定归属、去重、异常判定一样不少）；
  确认"无法核实"的置 `已剔除` 并留原因。

### 5.3 早年缺少书面交接的补建方式（裁决）

**裁决：采用"事实移交补建单"，不补造验收合格结论。**

1. 依据门槛：实际投运记录、首次接管巡检记录、资产/费用入账凭证，**三类凭证至少具备两类**；
   凭证清单逐条登记在补建单上。
2. 发起与会签：由接收单位发起，建设单位（或其权利义务承继单位）会签；
   建设主体已灭失的，由建设主管部门见证签认。
3. 单据标记：来源 = `补建-事实移交`，记载实际投运日、补建日期、依据凭证、会签/见证人。
4. 缺陷责任期：
   - 合同/设计文件/法规有约定的，从其约定（多档不一致时按 §4.3 取严）；
   - 无任何约定的，自实际投运日起**默认 24 个月**（参照《建设工程质量管理条例》基础设施、
     设备安装工程最低保修期限的精神与行业惯例；主体结构缺陷仍按法定保修与设计使用年限执行，
     不受 24 个月限制）。
5. 补建时已超过责任期的：**不得追溯认定"移交时合格"**——遗留问题一律先进待查台账人工核实，
   核实属实的转隐患整改；结论位保留 `待补验（补建）`，由会签各方按现状结论签认。
6. 补建单与正式单执行完全相同的归属规则，验收结论仍只归验收单位验收人。

## 6. 每笔数据绑定归属，写入即校验

- 所有写接口第一个参数是操作人（单位、姓名、角色），服务端（本地引擎）校验，不相信页面传参里的
  "归属单位"字段；归属以记录上持久化的值为准。
- 越权写入在落库前拒绝，不产生半成品数据；驳回原因写明归属冲突双方。
- 所有成功写入追加不可变操作日志（全局递增序号、操作人、单位、时间、事件类型、业务键、载荷）。

---

## 7. 同步：断线从断点续传，绝不顶上一条值

- 每条业务操作入库即分配**全局单调递增序号**进入发件箱。
- 同步游标 = 连续确认成功的最大序号。断线重连后，从 `游标 + 1` 那条**原事件**开始重放，
  按序号顺序确认；中间一条没成功，后面的不得跳过。
- 重放幂等：业务键（移交单编号、缺陷编号、待办编号）+ 事件序号双重去重，重复推送不产生重复效果。
- **禁止"拿上一次的值顶上"**：进来的事件若缺载荷/缺关键字段，不沿用上一条事件的值，
  原值保持不动，该事件挂待查台账（§2.2 第 6 项）。

---

## 8. 概览与看板：条数只有一个口径

- 全模块只有一个统计函数输出条数：移交单（有效/待验收）、受控待办（待办/到期）、
  本链路转入隐患数（直接读隐患整改模块的真实记录）、待查未结、缺项待确认、越权驳回数。
- 概览卡片、看板、各页角标全部引用这同一函数的同一返回；任一写入后两处同时刷新，
  **架构上不存在"两个数"的可能**（不是靠人工核对保证的）。

---

## 9. 口径速查

| 事项 | 裁决 |
| --- | --- |
| 验收结论谁能改 | 仅验收单位的验收人；其他单位只读，越权驳回并记归属冲突 |
| 缺陷判定打架 | 取更严一档；同级以接收单位为准；宽松档降级为提示 |
| 责任期内遗留问题 | 锁定即生成受控待办；到期未闭环自动转隐患（幂等） |
| 同编号重复提交 | 内容相同幂等丢弃；内容不同驳回并进待查 |
| 规则冲突 | 从严强制，从宽降级提示 |
| 存量移交单 | 按验收日期升序回填，走同一写入引擎 |
| 往期巡检数据 | 阶段 B 按巡检日期升序搬入，挂不到有效单的进缺项清单 |
| 缺失项 | 逐条列示、人工确认；确认前不计有效条数、不触发转隐患 |
| 早年无书面交接 | 事实移交补建：三类凭证至少二类、会签见证、默认责任期 24 个月、超期不追认为合格 |
| 同步断线 | 从最后未成功序号的原事件续传，缺值不顶上、挂待查 |
| 条数一致性 | 概览与看板共用唯一统计函数 |
